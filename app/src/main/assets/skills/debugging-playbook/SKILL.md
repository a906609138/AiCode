# 调试流程

## 何时使用

- 出现崩溃、异常、报错日志；
- 行为与预期不符；
- 偶发/难以复现的问题。

## 步骤

1. **先拿到完整证据，再动手**：
   - 完整堆栈（不要只看第一行），定位到具体文件与行；
   - 相关的应用日志（本项目用 `FileLogger`，落在外部私有目录 `.../files/logs/`，无需 root 即可读）；
   - 复现步骤：什么操作序列触发，是否稳定复现。
2. **判断问题层次**：构建期 / 运行期 / 数据 / 环境。别把运行期崩溃当构建问题查。
3. **形成假设并验证**，一次只改一个变量：
   - 看代码路径：读相关函数与调用链，找出「什么条件下会走到这里」；
   - 加日志或写最小复现（能写单测就用单测固定住问题）；
   - 用排除法：注释/简化可疑分支，看问题是否消失。
4. **定位根因，而不是现象**：问「为什么这里会是这个值/这个状态」。修在根因处，不要在症状处打补丁。
5. **修复后必须验证**：重跑复现步骤、跑相关测试、确认没有引入新问题；说明改了哪里、怎么验证的。
6. **如果查不到**：如实说查到哪一步、排除了什么、怀疑什么，并列出下一步需要什么信息（哪个日志、能否提供复现步骤）。不要编一个「可能的原因」当结论。

## 常见方向

- 空指针 / 越界 / 类型转换失败；
- 主线程做 IO 导致卡顿或 ANR；
- 并发：数据竞争、在错误线程访问、未取消的协程/监听；
- 生命周期：持有已销毁的 Context/Activity、回调在销毁后触发；
- 状态：初始值不对、状态没重置、缓存未失效。

## 注意

- 不要靠猜改代码——每次修改都应有明确的假设支撑。
- 不用 `try/catch` 吞掉异常来「消除」报错。
- 偶发问题优先怀疑并发与时序，别急着归因于「随机」。
