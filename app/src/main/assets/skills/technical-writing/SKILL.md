# 技术文档写作

## 何时使用

- 用户要求写或改文档（README、接口文档、使用指南、迁移说明等）；
- 需要把代码或零散笔记整理成读者能一次读懂的文档。

## 步骤

1. **先确认读者与目的**：这份文档给谁看、他看完要能做什么。读者是新人还是老手、要上手还是要查参数，写法完全不同。
2. **摸清事实**：描述真实代码/接口时，用 `readFile`/`search` 读到确切实现——参数名、默认值、返回值、错误行为都以代码为准，**不凭印象描述**。
3. **定骨架再填肉**：列出文档要回答的几个问题，按「读者最想先知道什么」排序。常见结构：这是什么/能做什么 → 怎么开始（可复制的最小示例）→ 常用操作 → 参数或配置说明 → 出错怎么办。
4. **面向任务写**：多写「要达成 X，这样做」，少写抽象定义。示例要完整、可直接复制，不留占位符。

## 输出格式

- 直接产出成稿，不写「以下是一份文档」这类套话开场。
- 需要交付文件时写成 Markdown 用 `writeFile`，并用 `sendFile` 送达；或按用户指定路径写入。
- 术语第一次出现时用读者能懂的话解释。

## 注意

- 不编造 API、参数或行为。查不到的写「未确认」，并说明查了哪里。
- 不夸大功能；做不到的事不写成「即将支持」。
- 不改动被描述的实现代码——职责是描述，不是修改。
- 限制、前提、不支持的情况要主动写出来。
