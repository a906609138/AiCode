# SQL 优化流程

## 何时使用

- 查询变慢，需要优化；
- 索引没生效，想知道为什么；
- 设计新表结构或评审迁移方案。

## 步骤

1. **先收集事实**：
   - 完整的 SQL（含参数）；
   - 表结构与已有索引；
   - 数据量级（行数、增长趋势）；
   - 执行频率与耗时。
2. **拿执行计划**（关键一步）：
   ```sql
   EXPLAIN ANALYZE <你的 SQL>;
   ```
   关注：是否全表扫描、用了哪个索引、扫描行数、回表次数、排序/临时表开销。
   **不要凭 SQL 长相猜瓶颈。**
3. **定位根因**，常见几类：
   - **缺索引**：WHERE/JOIN/ORDER BY 涉及的列没有合适索引；
   - **索引失效**：列被函数包裹、隐式类型转换、`LIKE '%x'` 前置通配、`OR` 混用；
   - **选择性差**：索引列区分度太低（如性别），优化器可能干脆不用；
   - **回表过多**：可用覆盖索引（把查询列并入索引）；
   - **查询本身**：`SELECT *`、深分页 `LIMIT 100000, 20`、不必要的排序与子查询。
4. **按优先级给方案**：
   - ① 改查询写法（通常收益最大、代价最小）；
   - ② 加/调索引；
   - ③ 改表结构（最后手段，代价最高）。
   每条都要说明**预期收益**与**代价**（写入变慢、空间占用）。
5. **评估迁移风险**：锁表时长、对在线业务影响、回滚方案；大表优先在线 DDL 或分批处理。

## 输出格式

```
## 问题
（现状 + 证据：执行计划关键行、耗时、数据量）
## 根因
## 优化方案
1. <做法> —— 预期收益 / 代价
## 迁移与回滚
```

## 注意

- 索引不是越多越好：写放大、空间、维护成本都是真实代价。
- 不在没有执行计划的情况下断言「加个索引就好了」。
- 破坏性操作（`DROP`/`DELETE`/`ALTER`）先说明影响并征得同意；生产库只做只读分析。
