# 接口与数据建模

## 何时使用

- 设计一组新接口或新服务；
- 评审已有 API 是否合理；
- 设计/修改数据表。

## 步骤

1. **先定领域模型，再定接口**：找出核心实体、关系、状态流转。数据模型错了，接口怎么改都是补丁。
2. **定义接口**，每个都要写清：
   - 资源/操作、路径、方法；
   - 请求参数（必填/可选、类型、取值范围、默认值）；
   - 响应结构（成功与失败分别长什么样）；
   - **错误码**：列出可能的失败及含义，不要只写 200；
   - **幂等性**：重复调用会怎样？是否需要幂等键？
3. **想清楚失败路径**：超时、部分成功、重试、并发写冲突时，调用方会看到什么、该怎么处理。
4. **数据表设计**：
   - 字段类型、可空性、默认值；
   - **索引**：按实际查询模式建（哪个字段过滤、哪个排序），并说明为什么；
   - 约束：唯一约束、外键、检查约束——能在数据库层保证的就别只靠应用层；
   - 迁移与兼容：加字段、改类型对已有数据的影响。
5. **一致性与并发**：哪些操作必须事务、哪些可以最终一致；并发写用乐观锁、唯一约束还是幂等键。

## 输出格式

```
## 领域模型
（实体、关系、状态流转）
## 接口
### <操作名>
- 请求：
- 成功响应：
- 失败：<错误码>: <含义>
- 幂等性：
## 数据表
### <表名>
| 字段 | 类型 | 可空 | 说明 |
- 索引：（字段 + 理由）
## 一致性与并发
## 风险与取舍
```

## 注意

- **不要设计没有需求支撑的扩展点**——「以后可能会用到」不是理由。
- 命名要一致：同一个概念全篇用同一个词。
- 分页、排序、过滤这些通用能力要明确约定，别每个接口各写一套。
- 破坏性变更要给出兼容方案与迁移步骤。
