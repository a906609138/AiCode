# 代码评审清单

## 何时使用

- 用户要求评审某段代码、某个提交或某个 PR；
- 你自己刚做完一处改动，提交前自查；
- 排查「这段代码为什么可能出问题」。

## 步骤

1. **拿到改动范围**：用 `git diff`（或用户指定的范围）看改了什么；没有 git 时直接读相关文件。
2. **读改动周边的真实代码**，不要只看 diff——一个改动是否安全取决于它周围怎么用。用 `search` 找出所有调用点确认影响面。
3. **按下面五项逐项过**，每项都要明确回答「有没有问题」：
   - **正确性**：正常路径逻辑是否成立？条件有没有写反、分支有没有漏、边界算没算错？
   - **边界与异常**：空值、空集合、长度为 0/1、极值、并发访问、IO 失败、超时——逐个问「这里会怎样」。
   - **资源与生命周期**：文件/连接/线程/订阅/协程是否都被正确释放？有无泄漏或重复释放？
   - **安全**：有无 SQL/命令注入、路径穿越、越权、凭据泄漏或外发。
   - **可维护性**：命名是否达意？是否与项目既有写法冲突？是否引入了不必要的抽象？
4. **验证而非猜测**：拿不准时运行测试、写最小复现，或读依赖源码；把「我推断」与「我验证过」分开说。

## 输出格式

先一句话给总体判断（能否合并 / 必须先修什么），然后分组：

- **必须修（会导致错误或安全问题）**：问题、触发条件、`文件路径:行号`、建议改法。
- **建议改（健壮性或可维护性）**：同上，说明为何不阻塞合并。
- **存疑（需作者确认）**：写出疑问，不要断言它是错的。

没有真实风险的地方不要发言。改动没问题就直接说没问题，别为凑数编意见。

## 注意

- 只评审、不擅自改文件；要展示改法就在回复里写片段。
- 不把个人风格偏好当成问题；先对齐项目既有约定。
- 不顺手评审无关代码。
